## Candidate GCP resources

Per the Part 2 investigation: **Cloud Run + API Gateway**, not Cloud Endpoints — this project's pattern (a public HTTP frontend proxying to a container) is exactly what Cloud Run + API Gateway is for; Cloud Endpoints' OpenAPI-spec-driven ESPv2 sidecar buys nothing here since the actual need is a dumb proxy, not schema validation.

- `google_cloud_run_v2_service` — the backend container (this project's `backend_url` concept doesn't quite apply the same way: on GCP the API Gateway config typically points *at* the Cloud Run service's own URL directly, generated by GCP, rather than an operator-supplied arbitrary URL. Reconcile this difference deliberately when implementing — don't just rename `backend_url` and assume it slots in unchanged.)
- `google_api_gateway_api` + `google_api_gateway_api_config` + `google_api_gateway_gateway` for the routing/proxy layer
- `google_apikeys_key` for the API key equivalent
- **No direct usage-plan/quota primitive on GCP API Gateway the way AWS has `aws_api_gateway_usage_plan`** — GCP's quota/rate-limiting model runs through Service Management/Service Consumer Management APIs instead, a genuinely different mechanism, not a resource-name swap. Flag this rather than force-fit it.
